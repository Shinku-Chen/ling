# AI 协作指南

面向在本仓库工作的 AI 助手：怎么建立上下文、边界在哪、交付什么。

## 1. 起步顺序

1. 读根 `AGENTS.md`（唯一规则入口）。
2. 按"任务路由"表读**最少**的文档，不要把所有 README 都加载一遍。
3. 改硬件相关事实前，先读 `docs/hardware/board-arcs-mini.md`；改运行时行为前，先读
   `docs/development/miniapp-runtime.md`。
4. 需要外部原始资料时，从 `docs/reference/README.md` 拿入口，不要自己猜 URL。

## 2. 三条边界（越界就是错误方向）

| 边界 | 属于本仓库 | 不属于本仓库 |
|---|---|---|
| 小应用 vs 固件 | Lua 代码、模拟器调试、adb 投放、文档 | 编译固件、改 `prc.conf`/pinmux/panel、烧录 boot、端侧 MCP 工具 |
| 本地 vs 云端 | 本地文件、模拟器、adb | 平台账号操作、应用/角色/知识库配置、云端下发审批 |
| 事实 vs 猜测 | 有来源的规格、实测结论 | "应该是这样"的推断——写"未核实"并去问 |

需要动固件或平台时：**停下来**，把入口和所需授权告诉用户，不要自己找路。

## 3. 写代码时的运行时不变式（最容易出错的地方）

- 没有 `pcall`：任何可能失败的外部输入都必须先判类型/判空，不要写"出错再说"。
- 没有 `require`：多文件靠 `src/bundle.conf` 合并；模块文件里不能有 `return`。
- 每帧预算有限：矩形 ≤128、文字 ≤8 段、每段 ≤63 字节；画面静态就不要每 tick 重画。
- 写入有节流：`storage` 同一槽 ≥10 秒一次，`tts` 同时只有 1 条，`http` 并发 ≤4。
- 时间可能没有：`clock.*` 未校时返回 nil；`on_tick` 的 `dt_ms` 才是唯一的稳定节拍。
- 副作用要克制：`on_start`/第一次 tick 里不要发网络或播报（TTS 明确禁止，网络会打乱首帧）。

## 4. 验证要求

改完代码必须跑 `.\tools\validate.ps1`（合并 + 静态检查 + 模拟器实跑）。
没有跑过的检查不能声称通过；模拟器过了也要在交付里点明"真机未验"的部分。

## 5. 交付格式

```text
Build: PASS / FAIL / NOT RUN
Static checks: PASS / FAIL / NOT RUN
Simulator run: PASS / FAIL / NOT RUN
Unverified: 需要真机/人工确认的项
```

汇报里同时说明：改了哪些文件、为什么这么改、有什么已知限制。
需求沟通的最终结论要回写到本仓库文档（不要只留在对话里）。

## 6. 文档纪律

- 一个事实一个真相源；改事实时同步改来源引用，不要制造第二份。
- 新增文档前先想清楚它归哪个目录；空壳文档不建。
- 中文正文用全角标点；代码、命令、路径、字段名保持 ASCII。
